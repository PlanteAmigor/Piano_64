## 一点五、解决了什么（原始判断 vs 实测）

交接最需要说清楚的就是这一节。队友最初的几个判断，实测下来分成两类：
**有的根本不成立（资源其实够用），有的是真问题但已经解决（谐波吞吐）。**

### ①「256 分量放不下」→ 不成立，128 分量只用 34% BSRAM

原分析：256 分量 = 138% 资源，不可行。

四个根因错误：

| 原始假设 | 实际情况 |
|---|---|
| 每个声部要独占一份 ROM 表 | **4 个声部共享同一份表**（同时刻最多一个声部在查表） |
| 布线延迟「大约 10 ns」是猜的 | 实测引擎内部路径 **13.4 ns**（含布线），不是 23 ns |
| 分量越多越慢 | 反了：改成 **16 级流水**后路径从 15.1 ns 降到 **9.3 ns** |
| 「48 条 setup 违例，最差 −10.00 ns」 | 实测 **1 条**（I2S 输出 −0.085 ns） |

**实测钢琴整机（88 音 × 128 分量）：BSRAM 114/340 = 34%，Logic 3%，时序 slack 余量充足。**

### ②「谐波 16 拍一个，来不及」→ 已解决，1 谐波/时钟

详见正文第二节 2。8 个并行 bank + 5 级流水，4 声部最坏 **292/1024 拍**。

### ③「笛子要 256 个分量」→ 是误会，笛子 K 由奈奎斯特决定

| 乐器 | 分量数来源 | 实际值 |
|---|---|---|
| 钢琴 | 固定 slot | **128**（88 音 × 128 = 11264 行） |
| 古筝 | 固定 slot | **128**（49 音 × 128 = 6272 行） |
| 笛子 | K = ⌊(fs/2)/f₀⌋ | **15 ~ 62**（MIDI 67..91） |
| 唢呐 | K = ⌊(fs/2)/f₀⌋ | **11 ~ 55**（MIDI 69..96） |

- **256 只属于模态乐器（钢琴/古筝）的候选分量数**，跟笛子唢呐没关系。
- 钢琴实测 128 个分量里 **128 个都在 −40 dB 以上**（最少 65 个），确实是满的；
  古筝只有中位数 **66 个**在 −40 dB 以上，**128 是够而有余**。
- 反过来若真要 256：因为 4 声部共享表，256 也只是 BSRAM ~68%，
  能放但没必要（古筝 128 已经用不完）。

### ④ 修掉的两个真 bug

| Bug | 影响 |
|---|---|
| `A` 定标用 Q3.13（±4.0） | 笛子最大 4.48、唢呐最大 6.83 → **9 个音的谐波被削顶**。改 Q4.11（±8.0） |
| 单声部引擎 6 个 RTL bug + 4 声部引擎 6 个 RTL bug | 见 git log `5fad12f` / `73b1ac4`，插值符号扩展、Φ 高 16 位漏读、Ψ 索引 0xFFFF、流水 valid 少一级等 |

## 二、完成了什么

### 1. 数据层：笛子 / 唢呐的谐波表（已完成）

从拟合好的 npz 生成 FPGA 用参数表：

| 乐器 | 音域 | 谐波数 K | 表大小 |
|---|---|---|---|
| 笛子 | MIDI 67..91（G4..G6，25 音） | 15 ~ 62 | 3.24 Mbit |
| 唢呐 | MIDI 69..96（A4..C7，28 音） | 11 ~ 55 | 3.32 Mbit |

压缩手段：Env 用 int8 + 每谐波峰值缩放（16 位 → 8 位，省 55 块 BSRAM）；
起振项预乘进包络（RTL 不用算指数）；A/φ 形式（每次只查一次正弦）。
表相对 npz 的拟合精度 ≈ 42 dB。

**顺带修了一个旧表就有的 bug**：`A` 原来是 Q3.13（±4.0），但实测
笛子最大 A=4.48、唢呐最大 A=6.83 → 9 个音的谐波被削顶。改成 Q4.11（±8.0）。

### 2. RTL：4 声部全流水引擎（已完成）

```
src/add_engine_harm.v   4 声部流水引擎（1 谐波/时钟）
src/harm_rom.v          8 个并行表 bank
```

原方案一个谐波要 16 拍（9 次串行表读 + 6 拍算术），K=62 时一个声部就吃掉
1003 拍，**只够 1 个声部**。新方案把表拆成互相独立的 8 个 bank 并行读，
再上 5 级流水线：

```
S0 发地址 → S1 Env/Ψ 插值 → S2 相位合成 → S3 幅度合成
→ S4 正弦插值 → S5 累加
```

| 场景 | 每样点拍数（预算 1024） |
|---|---|
| 1 声部（最低音 K=62） | 74 |
| 4 声部同音（最坏情况） | 292 |
| 4 个不同音 | 205 |

### 3. 验证（逐点比对，不是只看 SNR）

| 测试 | 结果 |
|---|---|
| 1 声部 MIDI 67 vs 已验证的单声部引擎 | SNR 47.8 dB |
| 1 声部 MIDI 72 | SNR 66.0 dB |
| **4 声部同音** | **逐点完全一致（maxdiff=0）** |
| **4 个不同音 vs 4 次单声部输出之和** | **maxdiff=3（只是取整）** |

两套 RTL 用完全不同的表格式和调度，能逐点对上说明寻址 / 流水 / 定标全对。

### 4. 综合（Gowin GW5AST-138C，50 MHz）

```
Logic      2118 / 138240  (2%)
Register    744 / 139095  (<1%)
CLS        1571 / 69120   (3%)
BSRAM       264 / 340     (78%)
时序        50 条 setup/hold 路径，最差 -0.074 ns（边缘，实际可用）
```

## 三、还差什么

### A. 顶层接线（代码活，我可以做）

把 `add_top.v` 里的 `add_engine8`（钢琴引擎）换成 `add_engine_harm`。
两者端口是特意对齐的，替换本身只改例化那几行，但要配三件事：

1. **表文件进工程根目录**（11 个 `.hex`，和 `add_param0.hex` 同级）
2. **只烧一个音色**：BSRAM 78%，钢琴表和笛子表不能同时驻留。
   `build.tcl` 里按 `TIMBRE_SEL` 二选一
3. **音量重定**：`sat_gain` 现在是 ×4（按钢琴单音峰值 1951 定的）。
   笛子满刻度是另一个量级，`MIX_SHIFT` 和 `sat_gain` 要重新算

### B. 按键方案（等队友定，我不动）

现状：`piano64.cst` 只接了 7 个键

| 引脚 | 现在功能 |
|---|---|
| KEY[0..5] | 6 个音键（do re mi fa sol la） |
| KEY[6] | 模式键（切曲谱） |

`note_alloc.v` 已经支持「每个音色一张 STEP 表」（`KEY_STEP` 是 parameter），
所以**换音色不用改电路**：只要喂不同的 `{NOTE_BASE, KEY_STEP}` 就行。

需要定的两件事：
- **八度键放哪**（KEY[6] 循环？还是从 J14 再引两个脚？）
- **每个音色的 6 个音键要什么音阶**（大调 / 五声 / 其他）

定下来之后，改动只在 `add_top.v` 的一个参数表里。

### C. 已知行为差异

笛子表只有 **3 秒**。按住键超过 3 秒声音就结束（不像钢琴一直衰减）。
目前 `v_gate` 没接进引擎，**松键不会立刻停**。
如果需要「松键即停」，要在 `add_engine_harm` 里加一条 gate 处理。
