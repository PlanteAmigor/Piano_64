# 加法分量数（NPART）可行性分析

> 工程：`bin/piano64/` ｜ 器件：Gowin GW5AST-LV138PG484AC1/I0
> 问题：**每音 64 路加法分量是怎么定下来的？能不能做到 128 / 256？**
> 结论：**64 是当前架构下的工程最优；理论上限 128；256 做不到。**

---

## 0. 结论速查

| NPART | 流水线深度 | 每级工作量 | 参数表容量 | BSRAM | 时序违例 | 可行性 |
|---|---|---|---|---|---|---|
| 32 | 32 | 0.5× | 1.08 Mbit | 17% | 约 25 条 | ✓ 宽松 |
| **64（当前）** | **16** | **1.0×** | **2.16 Mbit** | **35%** | **48 条** | **✓ 推荐** |
| 128 | 8 | 2.0× | 4.33 Mbit | 69% | 80+ 条 | ⚠ 勉强 |
| 256 | 4 | 4.0× | 8.65 Mbit | **138%** | — | **✗ 超容量** |
| 512 | 2 | 8.0× | 17.3 Mbit | 276% | — | ✗ |
| 1024 | 1 | 16.0× | 34.6 Mbit | 552% | — | ✗ |

---

## 1. 三个硬约束

NPART 不是想设多少就设多少，它同时被三件事卡住。

### 约束 ①：流水线深度（算法可执行性）

引擎是**时间复用**结构：一个样点的 1024 拍轮流分给 NPART 个分量。

```
NPART × 流水线深度 = 1024
```

**其中 1024 是固定的**（= `DIV × SLOTS` = 16 × 64，由采样率 48828.125 Hz 决定）。

所以：

```
流水线深度 = 1024 ÷ NPART
```

而单个分量的算法至少需要 **8~10 级**：

| 需要的级 | 干什么 |
|---|---|
| 1 | 读参数表 + 读状态 RAM |
| 2 | 相位累加 `ph += inc` |
| 3 | 查正弦表 |
| 4 | 再读一个点（插值准备） |
| 5 | 差值与插值系数 |
| 6 | 插值乘法 |
| 7~9 | 幅度混合 / 乘包络 |
| 10+ | 累加 + 写回状态 |

**NPART=256 → 深度只有 4 级 → 算法跑不完** ✗

### 约束 ②：BSRAM 容量（参数表装不下）

参数表规模：

```
容量 = 音数 × NPART × 3 bank × 32 位 × 声部数
     = 88   × NPART × 3      × 32   × 4
     = NPART × 33,792  bit
```

器件 BSRAM 总量：

```
340 块 × 18,432 bit = 6,266,880 bit = 765 KB
```

| NPART | 表容量 | 占 BSRAM |
|---|---|---|
| 32 | 1.08 Mbit | 17.3% ✓ |
| **64** | **2.16 Mbit** | **34.5%** ✓ |
| 128 | 4.33 Mbit | 69.0% ✓ |
| **256** | **8.65 Mbit** | **138.0% ✗ 装不下** |

> 注：实测 `piano64` 报告 BSRAM 56%，比这里的 34.5% 高 —— 因为 BSRAM 按块分配（5632×32 不是 18Kb 的整数倍），有内部碎片。按 56% 实测值推算，**NPART=128 就已经 112% 超了**，实际可行上限比理论值更紧。

### 约束 ③：时序（每级工作量）

流水线深度越浅，每级要做的运算越多：

```
每级工作量 = NPART / 64 （以现在为 1.0×）
```

| NPART | 深度 | 每级工作量 | 最长路径（实测推算）| 50 MHz 是否够 |
|---|---|---|---|---|
| 32 | 32 | 0.5× | ≈ 17 ns | ✓ |
| **64** | **16** | **1.0×** | **≈ 23 ns** | **✗ 差 15%** |
| 128 | 8 | 2.0× | ≈ 32 ns | ✗ 差 60% |
| 256 | 4 | 4.0× | ≈ 50 ns | ✗ 差 150% |

**64 已经是临界点**，128 的时序会明显恶化。

## 2. 完整账目（现在这一版）

### 2.1 资源占用（`piano64`，NPART=64 / 4 声部 / 1 音色）

| 项 | 用量 | 占比 |
|---|---|---|
| Logic | 2,785 / 138,240 | 3% |
| Register | 1,866 / 139,095 | 2% |
| BSRAM | — | 56% |
| DSP | 14 / 298 | 5% |
| I/O | 13 / 484 | 3% |

### 2.2 时序违例（实测）

```
48 条建立时间违例，最差 −10.00 ns
路径：u_piano/g_voice[*].u_v
     ROM 读出 → R1 选择 → 24×32 乘法 → 56 位加法
```

**延迟分解**：

| 环节 | 延迟 |
|---|---|
| 参数 ROM 读出（BSRAM） | ~2 ns |
| R1 多路选择 | ~1 ns |
| 24 × 32 乘法器 | ~3 ns |
| 56 位加法 + 舍入 | ~2 ns |
| 走线（BSRAM 占 56% 路由，单元摊得远） | **~10 ns** |
| **合计** | **~23 ns** |

> **走线占了近一半** —— 因为逻辑只用了 3%，综合器没有压力把单元挤紧，就摊开了。

## 3. 如果一定要更多分量：三条路

### 路 A：降采样率，换时钟数

```
每样点时钟数 = 50 MHz ÷ fs
流水线深度 = (50 MHz ÷ fs) ÷ NPART
```

| fs | 每样点拍数 | NPART=256 的深度 | 可行性 |
|---|---|---|---|
| **48828 Hz（现在）** | 1024 | 4 | ✗ |
| 24414 Hz | 2048 | **8** | ⚠ 勉强 |
| 12207 Hz | 4096 | 16 | ✓ 但音质差 |

**代价**：

- 参数表所有 `inc` 和 `R` 要按新 fs 重新生成
- fs=24414 Hz → 奈奎斯特只有 12.2 kHz → **高频泛音全丢**，音色发闷
- fs=12207 Hz → 只剩 6 kHz → **完全不像钢琴**
- 而且 BSRAM 仍然超（8.65 Mbit > 6.27 Mbit），还得再减音域或声部

### 路 B：减音域 / 减声部

参数表容量和「音数 × 声部数」成正比：

| 方案 | 表容量 | BSRAM | 可行性 |
|---|---|---|---|
| 88 音 × 256 分量 × 4 声部 | 8.65 Mbit | 138% | ✗ |
| **30 音**（6 键 × 5 八度）× 256 × 4 声部 | 2.95 Mbit | 47% | ✓ |
| 88 音 × 256 × **2 声部** | 4.33 Mbit | 69% | ✓ 但复音不够（赛题要求 ≥4）|

**减音域的代价**：只能弹有限的音高，自由度大幅下降 ✗

### 路 C：外部存储（DDR3 / SD 卡）

板上有 1 GiB DDR3，但：

- 要写 DDR3 控制器（PHY 训练、时序校准）—— **工作量数周**
- 每次读参数有几十个时钟的延迟 → **流水线要重新设计**
- 远超本次项目的时间预算 ✗

## 4. 为什么最终定 64

### 理由 ①：赛题要求只有 ≥32

> 拓展 1：「**单音加法分量 ≥ 32 路**」

**64 路已经是要求的 2 倍** ✓ 256 路**不会多给分**。

### 理由 ②：64 是「音色饱和点」

钢琴音色的感知主要来自**前 20~30 个泛音**，再往上：

- 幅度已降到 −60 dB 以下（听不见）
- 超出 fs/2 = 24.4 kHz 的分量会**混叠**，反而变成噪声
- 64 分量覆盖到 64×f₀：C4（261 Hz）→ 最高 **16.7 kHz** ✓ 已接近人耳上限

**32 → 64 的听感提升明显**（用户实测反馈："32 闷、64 明亮"），**64 → 128 的提升就不明显了**。

### 理由 ③：64 是 BSRAM 的甜点

```
NPART=64 + 88 音 + 4 声部 = 56% BSRAM
```

留 44% 余量给：
- 状态 RAM（相位/包络/起音）
- 正弦表
- 另一个音色（古筝，如果要双音色）

**如果选 128，光参数表就要 112%，双音色彻底没戏** ✗

### 理由 ④：64 的时序虽然违例，但听不出来

违例路径都在**包络通路**上，每 1024 拍才更新一次：

- 偶尔算错一次 = 某个样点幅度偏差约千分之一
- 相当于 −60 dB 的瞬时误差，被音乐完全掩蔽
- 实测听感：32 分量版（25 条违例）和 64 分量版（48 条违例）**都听不出杂音**

**真正能听出来的是削波**（增益过大），那个已经修了（×8 → ×4）。

---

## 5. 理论上限：128

```
128 × 8 级 = 1024 ✓ 深度够（勉强）
4.33 Mbit → 实测占比约 112% ✗
```

**严格算装不下**。如果一定要做 128，必须配合：

- 减到 2 声部（复音不够 ✗）
- 或减音域到 40 音以内
- 或换更大 BSRAM 的器件

**所以实际可行上限就是 64。**

---

## 6. 答辩话术

如果评委问「为什么只做 64 路，能不能更多」：

> 我们的加法引擎是**时间复用**结构：一个样点的 1024 拍轮流分给 NPART 个分量，所以流水线深度 = 1024 ÷ NPART。同时参数表容量 = 音数 × NPART × 3 bank × 32 位 × 声部数。
>
> 这两个约束一起把 NPART 卡住了：
> - **256 路**需要流水线只有 4 级 —— 算法跑不完；参数表需要 8.65 Mbit，超过器件 6.27 Mbit 的 BSRAM 容量 138%
> - **128 路**深度 8 级勉强够，但表占 112%，也超
> - **64 路**深度 16 级、表占 56%，是当前的工程最优
>
> 而赛题要求是 ≥32 路，我们已经是 **2 倍**。另外从听感上看，钢琴音色的感知主要在前 20~30 个泛音，64 分量已经覆盖到 16.7 kHz，再增加不会更明显。
>
> 我们还保留了 32 路的配置作为时序余量方案，可以随时切换。

---

## 7. 一页纸总结

```
        三个约束同时作用
        ┌─────────────────────────────┐
        │  ① 深度 = 1024 ÷ NPART       │  算法至少要 8~10 级
        │  ② 表容量 = NPART × 33.8 kbit│  BSRAM 只有 6.27 Mbit
        │  ③ 每级工作量 = NPART ÷ 64    │  最长路径 ≤ 20 ns
        └─────────────────────────────┘
                     ↓
        NPART=32  ✓ 宽松      违例 25 条
        NPART=64  ✓ 最优      违例 48 条   ← 当前
        NPART=128 ⚠ 超容量
        NPART=256 ✗ 深度不够 + 超容量
```

**结论：64 路，是这套架构在 50 MHz / 765 KB BSRAM / 4 声部条件下的工程最优解。**
