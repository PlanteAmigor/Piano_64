## 0. 目标

在教学页里直接从 **SD 卡**选曲，然后二选一：

| 模式 | 谁发声 | 人的角色 |
|---|---|---|
| **自动演奏** | 系统按曲谱自己弹 | 完全不参与（也可以做手势加表情） |
| **教学指导** | 人按键盘发声 | 跟着下落音符**按键**+**做手势** |

核心约定（用户确定）：

> **音色和音高都自适应，人只需要按键和手势。**

也就是说：

- **音色**由曲谱文件头决定，系统自动切，人不用按 AUX 切音色
- **音高**由曲谱事件直接驱动引擎的 `v_note`，**和按哪个键完全无关**
  （8 个物理键本来也覆盖不了几十个音高，这条彻底绕开了"8 键映射 / 换把位 / 转调"的麻烦）
- **键只做 gate**：按下 = 开始发当前音，松开 = 停
- **手势**叠加在曲谱音高之上：力度、滑音、颤音、指颤、顿音、急停照旧

## 2. 数据格式

### 2.1 SD 卡上的曲谱文件（一首歌一个文件）

```
扩展名 .P6S，放 SD 卡根目录
（sd_file_list_reader 只列根目录，所以不放子目录）

偏移   长度   字段
0x000  4      magic = "P6S1"
0x004  1      timbre        0=钢琴 1=古筝 2=唢呐 3=笛子
0x005  1      name_len      ASCII 文件名长度（≤31）
0x006  2      count         事件数 (LE16, ≤8192)
0x008  4      duration_ms   总时长 (LE32)
0x00C  4      transpose     建议移调半音数（有符号，可 0）
0x010  32     name_ascii    ASCII 名（不足补 0）
0x030  256    name_cn[8]    中文名点阵，8 字 × 16×16 bit（见 §2.4）
0x130  ...    events[count]
```

`event` 结构（**与队友 v3 协议完全一致，8 字节**）：

```
start_ms  u32 LE     相对曲首的毫秒
note      u8         MIDI 音高 21..108
dur_ms    u16 LE     1..65535
velocity  u8         1..127
```

- 事件按 `start_ms` 非递减排序
- 单文件最大 0x130 + 8192×8 = 65,792 B ≈ 64 KiB

### 2.2 DDR3 布局

| 区域 | 地址（256 位字） | 内容 |
|---|---|---|
| 音色表 | `0 .. 8769` | 现有：`piano_base=1`、`gz_base=5633`，每音 64 字 |
| **曲谱区（新增）** | `16384 起` | 每首最多 2048 字（64 KiB），预留 16 首 = 32768 字 |

- 上电时 `P64.BIN` 的加载流程**完全不动**
- `SONG` 加载在音源 ready **之后**、且**只在进入教学页时**触发，不拖慢上电

### 2.3 歌曲索引表（片内 RAM）

扫描 SD 时填，BSRAM 1 块（512×32）：

```
每项 8 B，最多 64 项
  file_num   u12    SD 根目录里的文件序号（op=1 用）
  timbre     u2
  count      u13
  duration_s u12    秒
  name_off   u9     指向名称存储区
```

名称存储：另 1 块 BSRAM（2048×8），存所有歌的 ASCII 名，每首 ≤32 B。

> 若想省掉这 2 块 BSRAM，可只存 `file_num`，列表显示 `01 02 03…`，选中后再读文件头取名字。**先按 2 块算，19 块空闲里拿 2 块可以接受。**

### 2.4 中文歌名（为什么不用字库）

`src/hdmi/ui/ui_font_cn.hex` 是**固定 22 字子集**（钢琴古筝唢呐笛子音名移调力度复八分量秒延迟帧），
全中文需 3000 字 × 32 B = 96 KB ≈ 48 块 BSRAM，而只剩 19 块。

所以**中文名做成点阵跟着文件走**：

- PC 端 `midi2p6s.py` 用 PIL 把歌名前 8 个汉字渲染成 16×16 位图写进 `name_cn[]`
- FPGA 侧只做 blit，不需要任何字库
- **加歌时自动带中文名，永远不用重新生成固件**

## 4. 显示设计（钢琴卷帘）

### 4.1 布局

```
整个屏幕 1280 × 720

  y=60   ┌──────────────────────────────────────────────┐
         │  歌名 / 音色 / 移调    [ 播放 | 演奏 ]  进度  │  ← 顶栏 (y 60..110)
  y=110  ├──────────────────────────────────────────────┤
         │                                              │
         │        钢琴卷帘区                            │
         │        纵轴 = 音高（32 半音窗口）            │
         │        横轴 = 时间（左 = 未来，右 = 现在）   │
         │   ┃                                          │
  y=640  └──────────────────────────────────────────────┘
         ┌───┐
         │判定线│ x = 1200（右侧，2 px）
         └───┘
```

- **卷帘区**：`x = 8..1196`，`y = 120..636`
- **判定线**：`x = 1200, 1201`（已有 `e_jline` 是水平线，改成垂直线）
- **音高窗口**：32 个半音，每半音 16 px（正好 512 px，y 从下往上）
  - 左下 = 曲谱当前窗口的最低音，`note -> lane = note - win_base`（0..31）
  - 超出窗口的音符贴边显示（sat）
- **八度线**：每 12 个半音画一条淡线（替代原来的 8 条轨道线）
- **黑键行底色**：可选用暗一点的颜色区分

### 4.2 横轴时间

- **左侧 = 未来，右侧 = 现在**（音符向右移动，撞到判定线发亮）
- 可见窗口 `W = 2000 ms`
- 横轴 `x` 映射到时间偏移 `dt = (1200 - x) / 1192 * 2000 ms`
  - `x = 1200` → `dt = 0`（现在）
  - `x = 8` → `dt ≈ 2000 ms`（2 秒后）

### 4.3 环缓冲（核心，几乎不花资源）

```verilog
// 256 列 × 32 bit（每列 = 那一时刻"哪几个音高在响"）
// 256 × 32 bit = 8 Kbit → 1 块 BSRAM
reg [31:0] note_col [0:255];
reg [7:0]  wp;          // 写指针

// 每 row tick（2000 ms / 256 = 7.8125 ms）一次：
//   t = now + 2000                          ← 前瞻
//   while (下一个事件.start_ms <= t) {
//        set note_col 临时掩码 [note - win_base]
//        lane_end[该音] = start_ms + dur_ms
//   }
//   for 32 个音高槽: if (lane_end <= t) 清位
//   note_col[wp] = 掩码;  wp++;
```

显示：

```
对像素 (x, y)：
   col_idx  = wp - (dt / 7.8125ms)        // dt 越大越靠左 → 索引越旧
   pitch    = (636 - y) / 16              // 0..31
   lit      = note_col[col_idx][pitch]
```

- **不用存未来、不用扫事件**，每 tick 只做 32 次比较
- "下落"是环指针推进自然产生的
- 长音 = 连续多列同一位 → 自然画出长条
- 每个音高槽对应的 `lane_end` 是 32 个 ms 计数器，纯寄存器

> 32 个音高槽 = 32 × 16 bit = 512 bit 寄存器，可以接受。

### 4.4 HDMI 读取时序

像素管线在 `clk_pix = 75 MHz`，每像素读一次 `note_col`：

- `col_idx` 由 `x` 决定 → 需要「x → 时间 → 索引」的乘法/查表
  - `dt` 与 `x` 是线性关系，`col_idx = wp - ((1200 - x) * 256) / 1192`
  - 用「预先算好的 256 项倒数表」或直接一个 `*256/1192` 的定点乘（数值很小，LUT 可承受）
- BSRAM 同步读 1 拍延迟 → 需要把像素坐标管线延迟 1 拍对齐
- **注意**：现在 HDMI 已经是 0 违例但很紧（之前加东西推到过 149 条违例），
  这块要按现有 UI 的多级流水风格来写（参考 `hdmi_ui3_top.v` 里 `liss` 的 5 级拆分）

## 5. 交互

### 5.1 进入教学页时

1. 显示「正在读取 SD 卡…」
2. 后台跑 `song_sd_scan`（`op=0`）
3. 扫完显示歌曲列表 / 或直接显示第 1 首的卷帘

> **为什么不在上电时扫**：`sd_file_list_reader` 要遍历根目录簇链，
> SD 里文件多时可能几秒；放在上电会让"音源 ready"看起来卡住。

### 5.2 按键

| 按键 | 作用 |
|---|---|
| `KEY_AUX[0]` 短按 | 下一首（循环） |
| `KEY_AUX[0]` 长按 | 进入「播放 / 演奏」选择，再短按切换，长按确认 |
| `KEY_AUX[1]` | 返回歌曲列表 / 停止 |
| `KEY.0` | 切页面（现有逻辑） |
| `KEY_AUX[0]` 超长按（3 s） | 重新扫描 SD（加歌后不用重启） |

> 具体按键在实现前再确认一次，避免和现有"AUX[0] 短按切音色"冲突
> （教学页里切音色由曲谱接管，所以可以复用）。

### 5.3 加载

选中歌 → `song_load`：

1. `op=1 read_file=file_num`
2. 边读边解析：头部存寄存器，事件流按 256 位字打包写 DDR3 曲谱区
3. 完成后置 `score_valid`

## 6. 两种模式的差异

| | 自动演奏 | 教学指导 |
|---|---|---|
| `eng_note` | 曲谱给 | 曲谱给（**与按哪个键无关**） |
| `eng_trig/gate` | 曲谱给 | **人按键**；漏按 → 系统兜底 |
| 力度 | 曲谱 `velocity` | 光学 `opt_vel` 优先，无人手时用曲谱值 |
| `hand_on` 门控 | **必须旁路**（否则没手就没声） | 保留 |
| 手势（bend/颤音/指颤） | 可用（加表情） | 可用 |
| 卷帘显示 | 有 | 有（多一个"你的按键"指示） |

**漏按兜底**：判定线处若该发声音但 `key_press` 没来，系统仍然 `trig` 发声，
只是把该音标记成"漏"（显示上变色 / 计入准确率），保证演奏不断。

## 10. 与蓝牙方案的取舍

队友已经做完 **BT36 蓝牙传曲谱 v3**（帧协议 + CRC + ACK + 8192 事件）。
本方案改成 **SD 卡 + 本地列表**，理由：

| | 蓝牙 v3 | SD 本方案 |
|---|---|---|
| 加歌 | 手机 App 上传，每次开机要重传 | 拷文件即可，掉电保存 |
| 依赖 | BT36 模块 + 手机 + App | 只要 SD 卡 |
| UI | 手机上选歌 | 板子本地选歌（符合赛题现场演示） |
| 曲谱 RAM | 需要 64 KiB BSRAM（**我们只剩 19 块，放不下**） | 走 DDR3 |
| 事件格式 | 8 字节/事件 | **完全兼容**，可直接复用他的 App 导出 |

> 结论：**事件格式保持兼容**，以后想加蓝牙也只是"多一个数据来源"，
> 把 `song_load` 的来源从 SD 换成 UART 帧解析即可。
